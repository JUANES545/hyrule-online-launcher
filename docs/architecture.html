Hyrule Online architecture

1. System context

The launcher is the control point. It runs hidden PowerShell scripts that start the two Cemu instances and drive the Milk Bar launcher to inject the mod, and it runs the dedicated server itself. Its input router writes a shared-memory block that the small XInput bridge in each Cemu folder reads. Apollo, Artemis and the SteamOS client are separate: nothing in src\ talks to Apollo or Artemis, and the Ally path was tried only against a temporary copy of the server.

2. Launcher internals

The six tabs (Play, Online, Graphics, World, Language, Details) sit on a set of services in one process. ServerHost owns the dedicated server and sends commands such as time, weather and name tags to its stdin; ServerEvents turns the server output into a roster of joined players. NetworkHint only classifies addresses and finds VPN adapters; nothing in the launcher probes a port, because any connection without a valid handshake kills the server, and a failed Join shows a fixed checklist. Everything that touches Cemu or the Milk Bar launcher goes through hidden PowerShell scripts. The setup wizard, the firewall rule and the shader cache are built but not verified on a clean machine or in game. Lines from tabs to services show the main uses only.

3. Play topologies

3a. Local

Local mode writes IP=127.0.0.1, port 5050 and an empty password into ServerConfig.ini, and runs one or two players on this PC. This is the base flow the project was built and used with.

3b. Host

Host mode binds the server to 0.0.0.0 with a port from 1024 to 65535 and a password, and builds the invite link hyrule://host:port?pw=. The launcher prefers a Tailscale address, then the home LAN address, and has an elevated button that adds an inbound TCP rule. A real second PC joining through this launcher, the player limit and the rule on a clean machine are not verified; only a TCP connect from the Ally to a temporary server copy on the LAN was.

3c. Join

Join mode parses an invite link or host:port, starts no server, and passes -RemoteServer host:port to Start-Online.ps1. Join now allows one or two local players. A real join through this launcher with a second machine is not verified.

3d. Ally hosts, PC joins with two players (script written, not verified)

The Ally runs the server and the PC joins with two local players while the Ally also plays. hyrule-online.sh --host is in the script: it binds the server to 0.0.0.0 (default port 5050), runs it under wine as the user unit hyrule-server with stdin kept open, shows hyrule:// invites for the LAN and VPN addresses (it only detects an active firewall, never changes it), then joins its own server on loopback unless --no-play is given. The whole path stays dashed: it has not run in a real three-player game, which RESEARCH.md lists as not verified. The server's player limit is 32, so three fit.

4. Session start

The launcher prepares displays, per-player Milk Bar settings and server rules, then runs Start-Online.ps1, which starts players one after another because the Milk Bar pipe \\.\pipe\languageConnectionPipe takes only two instances. A player counts as joined when %APPDATA%\BOTWM\LatestLog.txt shows Assigned to player and then a Displayed "Joined server line. The user still presses Continue in each Cemu window, because the mod's DLL scan needs it within about a minute. Dashed notes and lines are not verified: the host firewall step on a clean machine, and the stall restart in game.

5. Input path

  1. Physical pads (up to four) are read by SDL3 on a router thread, about every 4 ms. The router lives in the launcher; a headless InputRouter.exe does the same for scripts.
  2. The router assigns players to pads (player 1 to the first pad, player 2 to the second, with swap and re-assign) and writes the pad states, the two routes, a heartbeat and rumble commands to a 128-byte shared-memory block, Local\HyruleCoop.Routing.v2.
  3. A small native C DLL, xinput1_4.dll, is copied beside each Cemu.exe by Start-Online.ps1 in Routed mode. It answers XInput index 0 with player 1's pad and index 1 with player 2's pad, and reports no device for any other index. Each Cemu is therefore given only its own controller.
  4. If the router heartbeat is older than 5 seconds, the bridge falls back to the real XInput.
  5. Menu shortcut: default Start+LT held for 1.5 seconds, tracked per controller. While it is held the game sees the pad without those inputs, and a short rumble pulse confirms it. Start+Back is refused because Moonlight's quit combination includes it. While the launcher is in front of a running game, the games get a neutral pad.
  6. Status: simulated pads and the layout tests are verified; two real pads in Routed mode were confirmed by the user. Rumble in Routed mode and the shortcut with a physical pad through Steam Input or Moonlight are not verified.

6. SteamOS

6a. Installer

install.sh runs nine stages and records finished ones in ~/.config/hyrule-online/state. Options are --dry-run --yes --dump --mod --dir --link --uninstall. The game dump is supplied by the user and copied or linked, never downloaded. The CI job runs offline checks of these scripts; no run of the installer on a real device is recorded in RESEARCH.md.

6b. Join flow

hyrule-online.sh validates the host, port and name, then starts the Milk Bar CLI as a user systemd unit. It makes no TCP pre-check, on purpose, because any connection without a valid handshake kills the dedicated server. It reads client.log for SUCCESS or "Response":3, and also stops waiting if the unit ends. --stop stops the unit and runs wineserver -k. The Ally results in RESEARCH.md used a separate script (join.sh), so this script itself is not verified.

7. Release and CI

Pull requests to main or develop, and pushes to develop, release/** and hotfix/**, run two CI jobs: the Windows build, tests and packaging, and the offline SteamOS script tests on Linux. gitflow-guard.yml only lets release/* or hotfix/* into main, requires the branch name to match the VERSION file and an unused, newer tag, and limits what can enter develop and release/*. A push to main runs release.yml: it builds the setup and portable zip, packs the SteamOS tarball with its SHA-256, publishes a release, then merges main back into develop or opens a backport pull request.

Known limits

From RESEARCH.md unless marked otherwise.

  • A closed stdin makes the dedicated server spin and fill LatestLog.txt, so the launcher keeps stdin open.
  • Confirmed: any TCP connection that disconnects without a valid handshake (an empty connect, or a few junk bytes) kills the dedicated server with ArgumentOutOfRangeException in ServerData.GetPlayer, reproduced on the PC and on the Ally. So the launcher has no Test connection button and never probes a port, and a port scanner on the LAN could take a server down.
  • A real second PC joining through this launcher, the server's player limit, the right serversAdded entry when the list has several, and the firewall rule on a clean machine are not verified.
  • The Ally joined a temporary server copy over LAN ("Multiplayer session active", "Assigned to player 1"). Not confirmed: the character in the world on the Ally, a second player seen in both games, and the Windows launcher's own Join button.
  • A real three-player session (two on the PC plus the Ally) is not verified in game.
  • Physical pads through Steam Input or Moonlight are not verified. Start + LT may collide with ZL in play; Start + LT + RT or L3 + R3 are the fallbacks.
  • In the Ally client session, a D-pad press that opens an external window and Start closing the launcher have an unconfirmed cause; a key-guard defence is built but not verified there.
  • Player 2 sometimes stalls while loading; the restart of B (Cemu-Stall.ps1) is not confirmed in game.
  • The mod's DLL scan needs Continue pressed in about a minute, otherwise Cemu closes.
  • The Milk Bar pipe takes two instances, so players start one after another; three or four local players are not built.
  • Merging the mod with BCML is a manual boundary; BCML drops some files, which Patch-Mod.ps1 repairs.
  • The cause of the Milk Bar JSON "Unexpected character" corruption is not proven. DLL injection may trigger antivirus.
  • The shared shader cache is off by default and not verified in game. The FPS target needs a restart.
  • Rotation is not verified with a real pad or gameplay. Rumble in Routed mode is not verified.
  • Real Python and BCML installs, the multi-gigabyte downloads end to end, and the setup wizard on screen are not verified.
  • A Cemu keyboard profile crashes Cemu 1.26.2f.
  • Not covered by RESEARCH.md: the SteamOS CLI patch (start delay) and the Gaming Mode zenity dialogs. They come from steamos\install.sh and lib.sh and are unverified here.

Where the code and the docs differ

  • There is no README.md; CONTRIBUTING.md, RESEARCH.md and steamos\README.md are the written sources.
  • RESEARCH.md has no separate SteamOS section: the Ally results sit in the Online page section, and the install steps are documented only in steamos\README.md.
  • CONTRIBUTING.md lists only the installer and portable zip as release packages; ci.yml also tests the SteamOS scripts and release.yml also publishes the SteamOS tarball.
  • RESEARCH.md line for the Join page still says Join is one local player and that the player count goes back to two on leaving Join; a later bullet and the code (OnlineUi.cs: "One or two players") say Join allows one or two.
  • The World tab is called TabMultiplayer in the code.
  • hyrule-online.sh --host is in the script now, but RESEARCH.md does not describe it yet and it has not run in a game; topology 3d stays dashed.
  • No code in src\ configures Apollo, Artemis or a Steam shortcut on Windows; New-Shortcut.ps1 only makes a desktop shortcut. Streaming appears in RESEARCH.md only as Moonlight notes.
